1. Introduction

1.1 Overview of the Scenario

The Job Portal is a full-stack web application that connects three types of users: clients (who post jobs), freelancers (who apply and complete work), and administrators (who oversee the platform). The system supports the full lifecycle of a freelance engagement: job posting, application, status tracking, and payment processing.

Built on an Oracle Database backend with a Node.js/Express REST API and a vanilla HTML/CSS/JavaScript frontend, the application manages four core data entities — Users, Jobs, Applications, and Payments — alongside a dedicated audit/provenance layer.

1.2 Purpose of Provenance

Data provenance answers three fundamental questions about every piece of data in the system:

  • WHERE did the data come from? (origin / source of a record)
  • WHY was it changed? (reason and actor behind each modification)
  • HOW did it evolve over time? (full change history / lineage)

In a financial marketplace like this job portal, provenance is critical for accountability, dispute resolution, compliance, and debugging. For example: if a payment is flagged as "failed," provenance records reveal who initiated it, when the status changed, and what reason was logged — enabling administrators to investigate without guesswork.

This project implements provenance through a combination of Oracle audit tables, stored procedures, and triggers, all exposed through a GUI-based database explorer.

2. Database Design

2.1 Relational Schema

The schema contains four core tables and four corresponding audit tables, plus eight Oracle sequences.

Core Tables

Users (
  user_id   NUMBER PRIMARY KEY,
  name      VARCHAR2(100) NOT NULL,
  email     VARCHAR2(100) NOT NULL UNIQUE,
  role      VARCHAR2(20)  CHECK (role IN ('client', 'freelancer', 'admin')),
  password  VARCHAR2(100),
  created_at DATE DEFAULT SYSDATE
)

Jobs (
  job_id      NUMBER PRIMARY KEY,
  title       VARCHAR2(100) NOT NULL,
  description VARCHAR2(500),
  budget      NUMBER(10,2) NOT NULL,
  category    VARCHAR2(50),
  status      VARCHAR2(20) DEFAULT 'open'
              CHECK (status IN ('open','in-progress','completed','cancelled')),
  client_id   NUMBER NOT NULL REFERENCES Users(user_id),
  created_at  DATE DEFAULT SYSDATE
)

Applications (
  app_id         NUMBER PRIMARY KEY,
  job_id         NUMBER NOT NULL REFERENCES Jobs(job_id),
  freelancer_id  NUMBER NOT NULL REFERENCES Users(user_id),
  status         VARCHAR2(20) DEFAULT 'pending'
                 CHECK (status IN ('pending','accepted','rejected')),
  proposal       VARCHAR2(500),
  bid_amount     NUMBER(10,2),
  applicant_name VARCHAR2(100),
  created_at     DATE DEFAULT SYSDATE
)

Payments (
  payment_id     NUMBER PRIMARY KEY,
  job_id         NUMBER NOT NULL REFERENCES Jobs(job_id),
  amount         NUMBER(10,2) NOT NULL,
  payment_date   DATE DEFAULT SYSDATE,
  type           VARCHAR2(20) DEFAULT 'client_payment'
                 CHECK (type IN ('client_payment','freelancer_payout')),
  status         VARCHAR2(20) DEFAULT 'pending'
                 CHECK (status IN ('pending','completed','failed','refunded')),
  client_id      NUMBER REFERENCES Users(user_id),
  freelancer_id  NUMBER REFERENCES Users(user_id),
  transaction_id VARCHAR2(100),
  error_message  VARCHAR2(255),
  created_at     DATE DEFAULT SYSDATE
)

3. Audit Table Design

3.1 Description of Audit Tables

Each core table has a corresponding audit table that captures every INSERT, UPDATE, and DELETE operation with full before/after values, a timestamp, the actor who made the change, and the reason for the change.

Audit_Users

CREATE TABLE Audit_Users (
  audit_id       NUMBER PRIMARY KEY,
  user_id        NUMBER NOT NULL,
  old_role       VARCHAR2(20),
  new_role       VARCHAR2(20),
  operation_type VARCHAR2(10) CHECK (operation_type IN ('INSERT','UPDATE','DELETE')),
  timestamp      DATE DEFAULT SYSDATE,
  changed_by     VARCHAR2(100),
  change_reason  VARCHAR2(255)
);

Audit_Jobs

CREATE TABLE Audit_Jobs (
  audit_id       NUMBER PRIMARY KEY,
  job_id         NUMBER NOT NULL,
  old_status     VARCHAR2(20),
  new_status     VARCHAR2(20),
  old_budget     NUMBER(10,2),
  new_budget     NUMBER(10,2),
  operation_type VARCHAR2(10) CHECK (operation_type IN ('INSERT','UPDATE','DELETE')),
  timestamp      DATE DEFAULT SYSDATE,
  changed_by     VARCHAR2(100),
  change_reason  VARCHAR2(255)
);

Audit_Applications

CREATE TABLE Audit_Applications (
  audit_id        NUMBER PRIMARY KEY,
  app_id          NUMBER NOT NULL,
  job_id          NUMBER,
  freelancer_id   NUMBER,
  old_status      VARCHAR2(20),
  new_status      VARCHAR2(20),
  old_bid_amount  NUMBER(10,2),
  new_bid_amount  NUMBER(10,2),
  operation_type  VARCHAR2(10) CHECK (operation_type IN ('INSERT','UPDATE','DELETE')),
  timestamp       DATE DEFAULT SYSDATE,
  changed_by      VARCHAR2(100),
  change_reason   VARCHAR2(255)
);

Audit_Payments

CREATE TABLE Audit_Payments (
  audit_id        NUMBER PRIMARY KEY,
  payment_id      NUMBER NOT NULL,
  job_id          NUMBER,
  old_amount      NUMBER(10,2),
  new_amount      NUMBER(10,2),
  old_type        VARCHAR2(20),
  new_type        VARCHAR2(20),
  old_status      VARCHAR2(20),
  new_status      VARCHAR2(20),
  operation_type  VARCHAR2(10) CHECK (operation_type IN ('INSERT','UPDATE','DELETE')),
  timestamp       DATE DEFAULT SYSDATE,
  changed_by      VARCHAR2(100),
  source_table    VARCHAR2(50),
  affected_row_id NUMBER
);

4. Trigger / Procedure Implementation

4.1 Stored Procedures

Stored procedures encapsulate all DML operations and ensure provenance is always recorded together with the data change — atomically, inside a single transaction.

Procedure: insert_user_p

Called during user registration. Inserts a new record into the Users table using the user_seq sequence for the primary key. 

CREATE OR REPLACE PROCEDURE insert_user_p (
    p_name     IN VARCHAR2,
    p_email    IN VARCHAR2,
    p_role     IN VARCHAR2,
    p_password IN VARCHAR2
) AS
BEGIN
    INSERT INTO Users (user_id, name, email, role, password)
    VALUES (user_seq.NEXTVAL, p_name, p_email, p_role, p_password);
    COMMIT;
END insert_user_p;
/

Explanation: The trg_user_insert trigger fires automatically after this INSERT and writes the registration event (with role and actor name) to Audit_Users.

Procedure: update_job_status_p

Called when a job's lifecycle status changes (e.g., from "open" to "in-progress"). Captures the old status before updating, then writes both old and new values — along with the actor and reason — to the Audit_Jobs table. 

CREATE OR REPLACE PROCEDURE update_job_status_p (
    p_job_id      IN NUMBER,
    p_new_status  IN VARCHAR2,
    p_changed_by  IN VARCHAR2,
    p_reason      IN VARCHAR2
) AS
    v_old_status VARCHAR2(20);
BEGIN
    SELECT status INTO v_old_status FROM Jobs WHERE job_id = p_job_id;

    UPDATE Jobs SET status = p_new_status WHERE job_id = p_job_id;

    INSERT INTO Audit_Jobs (audit_id, job_id, old_status, new_status,
                             operation_type, timestamp, changed_by, change_reason)
    VALUES (audit_job_seq.NEXTVAL, p_job_id, v_old_status, p_new_status,
            'UPDATE', SYSDATE, p_changed_by, p_reason);

    COMMIT;
END update_job_status_p;
/

Procedure: update_job_budget_p

Called when a client revises the budget of a posted job. Records the previous budget for historical comparison. 

CREATE OR REPLACE PROCEDURE update_job_budget_p (
    p_job_id     IN NUMBER,
    p_new_budget IN NUMBER,
    p_changed_by IN VARCHAR2,
    p_reason     IN VARCHAR2
) AS
    v_old_budget NUMBER(10,2);
BEGIN
    SELECT budget INTO v_old_budget FROM Jobs WHERE job_id = p_job_id;

    UPDATE Jobs SET budget = p_new_budget WHERE job_id = p_job_id;

    INSERT INTO Audit_Jobs (audit_id, job_id, old_budget, new_budget,
                             operation_type, timestamp, changed_by, change_reason)
    VALUES (audit_job_seq.NEXTVAL, p_job_id, v_old_budget, p_new_budget,
            'UPDATE', SYSDATE, p_changed_by, p_reason);

    COMMIT;
END update_job_budget_p;
/

Procedure: update_application_status_p

Handles when a client accepts or rejects a freelancer's application. Retrieves the related job and freelancer IDs alongside the old status to provide full context in the audit record. 

CREATE OR REPLACE PROCEDURE update_application_status_p (
    p_app_id     IN NUMBER,
    p_new_status IN VARCHAR2,
    p_changed_by IN VARCHAR2,
    p_reason     IN VARCHAR2
) AS
    v_old_status   VARCHAR2(20);
    v_job_id       NUMBER;
    v_freelancer_id NUMBER;
BEGIN
    SELECT status, job_id, freelancer_id
    INTO v_old_status, v_job_id, v_freelancer_id
    FROM Applications WHERE app_id = p_app_id;

    UPDATE Applications SET status = p_new_status WHERE app_id = p_app_id;

    INSERT INTO Audit_Applications (audit_id, app_id, job_id, freelancer_id,
                                     old_status, new_status, operation_type,
                                     timestamp, changed_by, change_reason)
    VALUES (audit_app_seq.NEXTVAL, p_app_id, v_job_id, v_freelancer_id,
            v_old_status, p_new_status, 'UPDATE', SYSDATE, p_changed_by, p_reason);

    COMMIT;
END update_application_status_p;
/

Procedure: insert_payment_p

Initiates a new payment record. Simultaneously logs the payment creation event in Audit_Payments, recording the initial "pending" status and the initiating user. 

CREATE OR REPLACE PROCEDURE insert_payment_p (
    p_job_id        IN NUMBER,
    p_amount        IN NUMBER,
    p_type          IN VARCHAR2,
    p_client_id     IN NUMBER,
    p_freelancer_id IN NUMBER,
    p_changed_by    IN VARCHAR2
) AS
BEGIN
    INSERT INTO Payments (payment_id, job_id, amount, type, status, client_id, freelancer_id)
    VALUES (payment_seq.NEXTVAL, p_job_id, p_amount, p_type, 'pending',
            p_client_id, p_freelancer_id);

    INSERT INTO Audit_Payments (audit_id, payment_id, job_id, new_amount, new_type,
                                 new_status, operation_type, timestamp, changed_by,
                                 source_table, affected_row_id)
    VALUES (audit_payment_seq.NEXTVAL, payment_seq.CURRVAL, p_job_id, p_amount,
            p_type, 'pending', 'INSERT', SYSDATE, p_changed_by, 'Payments', p_job_id);

    COMMIT;
END insert_payment_p;
/

Procedure: update_payment_status_p

Updates a payment's status (e.g., "pending" → "completed" or "failed") and records the transition in Audit_Payments with the responsible user's identity. 

CREATE OR REPLACE PROCEDURE update_payment_status_p (
    p_payment_id IN NUMBER,
    p_new_status IN VARCHAR2,
    p_changed_by IN VARCHAR2,
    p_reason     IN VARCHAR2
) AS
    v_old_status VARCHAR2(20);
    v_job_id     NUMBER;
BEGIN
    SELECT status, job_id INTO v_old_status, v_job_id
    FROM Payments WHERE payment_id = p_payment_id;

    UPDATE Payments SET status = p_new_status WHERE payment_id = p_payment_id;

    INSERT INTO Audit_Payments (audit_id, payment_id, job_id, old_status, new_status,
                                 operation_type, timestamp, changed_by,
                                 source_table, affected_row_id)
    VALUES (audit_payment_seq.NEXTVAL, p_payment_id, v_job_id, v_old_status,
            p_new_status, 'UPDATE', SYSDATE, p_changed_by, 'Payments', p_payment_id);

    COMMIT;
END update_payment_status_p;
/

4.2 Triggers

Triggers provide automatic, database-level provenance capture. The design avoids double-logging: where a stored procedure already inserts an audit record, the corresponding trigger body is left intentionally empty (NULL) to prevent duplicate entries.

trg_user_insert — Automatic registration audit

CREATE OR REPLACE TRIGGER trg_user_insert
AFTER INSERT ON Users
FOR EACH ROW
BEGIN
    INSERT INTO Audit_Users (audit_id, user_id, old_role, new_role,
                              operation_type, timestamp, changed_by, change_reason)
    VALUES (audit_user_seq.NEXTVAL, :NEW.user_id, NULL, :NEW.role,
            'INSERT', SYSDATE, :NEW.name, 'User registered');
END;
/

Explanation: Fires on every user registration. Captures the newly assigned role (:NEW.role) and the user's name as the actor. The old_role is NULL since no previous value exists for a new record.

trg_application_insert — Automatic application submission audit

CREATE OR REPLACE TRIGGER trg_application_insert
AFTER INSERT ON Applications
FOR EACH ROW
BEGIN
    INSERT INTO Audit_Applications (audit_id, app_id, job_id, freelancer_id,
                                     new_status, new_bid_amount, operation_type,
                                     timestamp, changed_by)
    VALUES (audit_app_seq.NEXTVAL, :NEW.app_id, :NEW.job_id, :NEW.freelancer_id,
            :NEW.status, :NEW.bid_amount, 'INSERT', SYSDATE, USER);
END;
/

Explanation: Fires whenever a freelancer submits a job application. Captures the initial bid amount and status ("pending"). Uses the Oracle built-in USER pseudo-column as the actor identifier.

trg_payment_insert — Automatic payment creation audit

CREATE OR REPLACE TRIGGER trg_payment_insert
AFTER INSERT ON Payments
FOR EACH ROW
BEGIN
    INSERT INTO Audit_Payments (audit_id, payment_id, job_id,
                                 old_status, new_status,
                                 old_amount, new_amount,
                                 old_type, new_type,
                                 operation_type, timestamp, changed_by,
                                 source_table, affected_row_id)
    VALUES (audit_payment_seq.NEXTVAL, :NEW.payment_id, :NEW.job_id,
            NULL, :NEW.status, NULL, :NEW.amount, NULL, :NEW.type,
            'INSERT', SYSDATE, 'SYSTEM', 'Payments', :NEW.payment_id);
END;
/

Explanation: Fires on every new payment row. Records NULL for all "old" fields since this is an initial insertion, labels the actor as 'SYSTEM', and stores the source table name for cross-table traceability.

Design Note: Triggers for UPDATE operations on Jobs, Applications, and Payments have empty bodies (NULL). This is intentional — the corresponding stored procedures (update_job_status_p, update_application_status_p, update_payment_status_p) already write the audit record with richer metadata (actor name, change reason). Allowing both trigger and procedure to log would create duplicate audit entries.

5. Provenance Queries

Query 1 — WHERE Provenance: Origin of a Job

Provenance Type: WHERE — Identifies where a job record came from (which client, when, and under what initial conditions).

-- WHERE provenance: Full origin trace for a specific job
SELECT
    j.job_id,
    j.title,
    j.category,
    j.budget,
    j.status           AS current_status,
    j.created_at       AS job_posted_on,
    u.user_id          AS client_id,
    u.name             AS client_name,
    u.email            AS client_email
FROM Jobs j
JOIN Users u ON j.client_id = u.user_id
WHERE j.job_id = 1;

Interpretation: This query answers "Where did Job #1 come from?" by joining the job back to the client who posted it. The result shows the client's full identity, when the job was posted, and its original budget and status — establishing a clear origin record.

Query 2 — WHY Provenance: Reason Behind Job Status Changes

Provenance Type: WHY — Explains the reasoning and actor behind every status transition for a job.

-- WHY provenance: Full reason history for all status changes on a job
SELECT
    aj.audit_id,
    aj.job_id,
    aj.old_status,
    aj.new_status,
    aj.changed_by,
    aj.change_reason,
    aj.timestamp
FROM Audit_Jobs aj
WHERE aj.job_id = 1
ORDER BY aj.timestamp ASC;

Interpretation: This query answers "Why did Job #1 change status?" by retrieving every entry in the Audit_Jobs table for that job, in chronological order. Each row records who made the change, from which state to which state, and the human-readable reason — critical for dispute resolution.

Query 3 — HOW Provenance: Payment Lifecycle Trace

Provenance Type: HOW — Traces how a payment evolved from creation through completion or failure.

-- HOW provenance: Step-by-step payment evolution for a specific payment
SELECT
    ap.audit_id,
    ap.payment_id,
    ap.job_id,
    ap.operation_type,
    ap.old_status,
    ap.new_status,
    ap.old_amount,
    ap.new_amount,
    ap.changed_by,

WHERE ap.payment_id = 1

Query 4 — Combined Provenance: Full Job Timeline (WHY + HOW + WHERE)

Provenance Type: Combined — Produces a unified chronological audit trail for a job, merging events from Jobs, Applications, and Audit_Jobs.

-- Combined timeline for job_id = 1
SELECT 'Job Posted' AS event_type,
       j.job_id    AS entity_id,
       j.title     AS description,
       j.created_at AS event_time,
       'N/A'        AS actor
FROM Jobs j WHERE j.job_id = 1

UNION ALL

SELECT 'Application Submitted',
       a.app_id,
       a.proposal,
       a.created_at,
       a.applicant_name
FROM Applications a WHERE a.job_id = 1

UNION ALL

SELECT 'Status Changed to: ' || aj.new_status,
       aj.job_id,
       aj.change_reason,
       aj.timestamp,
       aj.changed_by
FROM Audit_Jobs aj WHERE aj.job_id = 1

ORDER BY event_time ASC;

Interpretation: This query produces a merged timeline of all significant events for a single job — from posting, through freelancer applications, to each status change. It directly supports auditors and admins who need to reconstruct the full history of a job engagement without querying multiple tables separately.

Query 5 — WHERE Provenance: Freelancer Activity Audit Trail

Provenance Type: WHERE — Identifies where (which jobs) a freelancer has been active and how their application statuses evolved.

-- WHERE provenance: All application events by a specific freelancer
SELECT
    u.name              AS freelancer_name,
    aa.app_id,
    aa.job_id,
    aa.new_status       AS current_status,
    aa.new_bid_amount   AS bid_amount,
    aa.operation_type,
    aa.timestamp,
    aa.changed_by
FROM Audit_Applications aa
JOIN Users u ON aa.freelancer_id = u.user_id
WHERE aa.freelancer_id = 2
ORDER BY aa.timestamp DESC;

Interpretation: This query traces all provenance events associated with a specific freelancer across every job they have touched. It shows who processed each status change, enabling HR or admin teams to monitor freelancer engagement patterns and detect unusual activity.

6. GUI Tool

6.1 Functionality Description

The project includes a browser-based Database Explorer accessible at /client/public/htmlfiles/viewProvenance.html. It is powered by the /api/explorer REST endpoint defined in server/routes/explorer.js.

The GUI tool provides the following capabilities:

  • Table Selector: A dropdown listing all 8 allowed tables (4 core + 4 audit). The allowed list is enforced server-side via a whitelist to prevent SQL injection.
  • Live Data View: On selecting a table, the frontend calls GET /api/explorer/:tableName, which fetches the most recent 100 rows ordered by primary key descending.
  • Column Headers: Dynamically rendered from Oracle's metaData field, so the UI adapts automatically to any table's column structure.
  • NULL Handling: NULL values are rendered as the string "null" for readability.
  • Admin Access: The explorer is intended for admin-role users who need to inspect raw data and audit trails.

7. Challenges and Lessons Learned

7.1 Avoiding Duplicate Audit Records

Challenge: Oracle triggers fire automatically on any DML, but stored procedures also write audit records. Without careful coordination, every UPDATE Jobs call from a stored procedure would produce two rows in Audit_Jobs — one from the procedure and one from the trigger.

Solution: UPDATE triggers were intentionally left with empty NULL bodies. Only INSERT triggers were given active bodies (for cases where no corresponding stored procedure writes the audit). This required disciplined documentation within the schema SQL file to explain why triggers appear to "do nothing."

7.2 Capturing Application-Level User Identity in Triggers

Challenge: Oracle's built-in USER pseudo-column inside a trigger returns the database user (e.g., SYSTEM or the schema owner), not the application-level user who clicked a button in the browser. For meaningful "changed_by" values, provenance must be passed from the application layer.

Solution: Stored procedures accept a p_changed_by parameter that carries the authenticated user's name from the Node.js backend. INSERT triggers that fire without a corresponding procedure (like trg_application_insert) fall back to USER, which is acceptable for system-level logging of new submissions.

7.3 Oracle Sequence Management

Challenge: Oracle does not support auto-increment columns the same way MySQL or PostgreSQL do. Each table required a separate sequence (user_seq, job_seq, etc.) and each audit table required its own sequence (audit_user_seq, etc.) — 8 sequences in total.

Lesson: Centralising sequence usage inside stored procedures (not in application code) keeps the sequence logic in the database layer, ensuring correctness even if multiple Node.js server instances run concurrently.

7.4 REST API Security for the Explorer

Challenge: Exposing a generic "query any table" endpoint is a severe SQL injection risk if table names are passed directly into a query string.

Solution: The explorer.js route implements a server-side whitelist (ALLOWED_TABLES object). Any table name not in this whitelist returns an HTTP 400 error. This prevents attackers from passing arbitrary table names or SQL fragments through the URL parameter.

8. Conclusion

8.1 Summary of Contributions

This project successfully demonstrates a complete provenance-enabled database system integrated into a real-world web application. Key contributions include:

  • A relational Oracle schema of 4 core tables and 4 audit tables with comprehensive before/after tracking.
  • 6 stored procedures that combine DML operations with atomic provenance logging.
  • 7 triggers that provide automatic provenance capture at the database level, with a dual-logging-prevention design pattern.
  • 5 provenance queries that address WHERE, WHY, and HOW provenance dimensions across all core entities.
  • A GUI-based Database Explorer with a security-hardened whitelist API for admin-level provenance inspection.
  • A full-stack web application (Node.js + Express + HTML/CSS/JS) that exercises all provenance features through realistic user workflows.

8.2 Future Scope

  • DELETE provenance: Current triggers do not capture DELETE operations. Adding BEFORE DELETE triggers on all core tables would complete the provenance picture.
  • Role-based audit access: The explorer currently requires manual admin access. A dedicated audit dashboard with role-based filtering and date-range queries would improve usability.
  • Provenance graph visualization: Rendering the audit trail as a directed acyclic graph (DAG) would allow users to visually trace data lineage across entities.
  • Oracle Workspace Manager: Oracle's built-in versioning tool could replace custom audit tables for even richer historical querying.
  • Automated provenance tests: Unit tests that verify audit rows are created correctly after each procedure/trigger call would harden the implementation against regressions.
